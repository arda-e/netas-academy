# Multi-Agent Orchestration Harness for Wave 4 Parallel Delegation

## Goal

Build a reusable multi-agent orchestration harness capable of autonomously executing the Wave 4 refactor defined in `docs/plans/2026-05-03-001-refactor-wave4-parallel-delegation-plan.md`. The harness provides: (1) a task decomposition engine that parses the plan into atomic executable units; (2) a state management system to track progress, dependencies, and file ownership across parallel threads; (3) a validation layer that verifies code integrity and plan compliance after each task; and (4) a supervisor agent that manages concurrency, error recovery, and integration reconciliation.

Focus is on the **infrastructure for autonomous execution** — not on implementing the Wave 4 content itself.

### 1.1 Design Principles

- **No runtime service**: The harness is a set of agent definitions, state schemas, and validation contracts — not a background daemon. The supervisor agent embodies the orchestration logic.
- **Plan-driven**: All task decomposition, dependency ordering, and file ownership boundaries derive from the plan document. No hardcoded unit knowledge.
- **Idempotent state**: The state file is the single source of truth. The supervisor can resume from any interruption by reading current state.
- **Explicit ownership**: Every file touched by the refactor has exactly one owning unit at any time. Shared files are managed through declared handoffs and Unit 9 reconciliation.
- **Composable validation**: Validation rules are declarative and organized by unit. The supervisor runs them after each worker and before marking completion.

### 1.2 Relationship to Existing Infrastructure

This harness extends — not replaces — the existing patterns:

| Existing | Harness adds |
|----------|-------------|
| `.kilo/agent/lead-architect.md` — orchestrates audits | `.kilo/agent/wave4-supervisor.md` — orchestrates refactor execution |

| `docs/plans/*-parallel-subagent-execution-units.md` | Generalizable infrastructure for any plan of this pattern |

## 3. Proposed Implementation

### 3.1 Component 1: Task Decomposition Engine

**Location**: Embedded in `.kilo/agent/wave4-supervisor.md` (Section: "Plan Parsing Protocol")

The supervisor agent receives instructions to parse the plan document and extract structured task units. The decomposition is not a separate program — it is a protocol the supervisor follows.

#### 3.1.1 Extraction Targets

For each unit (U00-U09) in the plan, the supervisor extracts:

```
TaskUnit:
  unitId              e.g., "U00", "U01", ...
  prId                e.g., "P3-02", "P4-01", ...
  title               From plan heading
  goal                From plan "Goal:" line
  wave                0=explorer, 1=parallel, 2=integration
  dependencies:
    upstreamUnits     e.g., ["U00"]
    upstreamGates     e.g., ["P3-01 merged", "P1-01 settled"]
  fileOwnership:
    modify            Repo-relative paths to edit
    create            Repo-relative paths to create
    handoff           Files this unit may discover need changes
    test              Test files to create/modify
  approach            Key constraints and approach notes
  validationScenarios
  verificationCriteria
  subagentRole        "explorer" | "frontend" | "backend" | "integration"
  sharedFileConflicts From plan's Shared Conflict Matrix (file, units, ownershipRule)
```

#### 3.1.2 Dependency DAG Construction

The supervisor builds a dependency graph:

```
U00 (explorer) ──┬── U01 (P3-02 Zod)
                 ├── U02 (P3-03 cache)
                 ├── U03 (P4-01 shells)
                 ├── U04 (P4-02 images)
                 ├── U05 (P4-03 perf)
                 ├── U06 (P4-04 backend perf)
                 ├── U07 (P6-02 proxy/logging)
                 └── U08 (P5-05 plugin) ← also gated by P1-01

U01..U08 ──► U09 (integration)
```

The supervisor computes:
- **Ready set**: units whose all upstream dependencies are satisfied
- **Blocked set**: units waiting on dependencies or handoffs
- **In-progress set**: units currently dispatched to workers
- **Completed set**: units that passed validation

#### 3.1.3 Plan Parsing Protocol

The supervisor reads the plan document line-by-line and applies these extraction rules:

1. **Unit boundaries**: Markdown `- [ ] **Unit N: PR-ID Title**` headings
2. **Goal**: Line starting with `**Goal:**`
3. **Dependencies**: `**Dependencies:** Unit N` or `**Dependencies:** Unit 0 and P1-01...`
4. **Files**: Lines under `**Files:**` matching `- Modify:`, `- Create:`, `- Handoff:`, `- Test:`
5. **Approach**: Lines under `**Approach:**`
6. **Test scenarios**: Lines under `**Test scenarios:**`
7. **Verification**: Lines under `**Verification:**`
8. **Conflict matrix**: Table under `## Shared Conflict Matrix` mapping `file | units | ownership rule`

#### 3.2.3 State File Bootstrap

The initial state file is populated by manually transcribing the 10 units from the plan. This is done once by the supervisor during initialization (Phase 0). The supervisor:

1. Reads the plan document
2. Extracts units using the parsing protocol (Section 3.1.3)
3. Writes `wave4-state.json` with all units in `pending` status
4. Populates `conflictMatrix` from the plan's Shared Conflict Matrix table
5. Seeds `fileLocks` as an empty object

#### 3.2.4 Lock Protocol

Before dispatching a worker, the supervisor acquires file locks:
1. Check each file in the unit's `modify` and `create` lists against `fileLocks`
2. If any file is locked by another in-progress unit → mark unit as `blocked` with reason
3. If all files are free → set `fileLocks[file] = unitId` for each file
4. On worker completion → release locks for that unit

Shared files from the conflict matrix get special treatment: multiple units may hold a "shared lock" but each is restricted to their concern (validation, cache, logging, etc.). Unit 9 has exclusive lock during reconciliation.

### 3.3 Component 3: Validation Layer

**Location**: `.kilo/orchestrator/wave4-validation-rules.md`

#### 3.3.1 Validation Rule Structure

Each rule has:
- **`id`**: unique identifier (e.g., `V-U01-01`)
- **`unitId`**: which unit this validates
- **`phase`**: `pre-dispatch` | `post-edit` | `post-build` | `integration`
- **`type`**: `build` | `lint` | `test` | `schema` | `manual` | `cross-cutting`
- **`command`**: bash command to run (for automated checks)
- **`expectedOutput`**: what constitutes a pass (exit code, text match)
- **`onFailure`**: `block` | `warn` | `retry`

#### 3.3.2 Rule Categories

**Pre-dispatch gates** (run before dispatching any worker):
- All upstream dependencies are satisfied (state check)
- No other in-progress unit holds an exclusive lock on shared files
- P1-01 gate for Unit 8 (explicit check)
- `backend/tests/FAILING_TESTS.md` classified for Units 6/8

**Post-edit automated gates** (per stack):

| Units | Gate | Command | Expected |
|-------|------|---------|----------|
| U01-U05, U07 | Frontend build | `npm run build:frontend` | exit 0 |
| U01-U05, U07 | Frontend lint | `npm run lint` | exit 0 |
| U01-U05, U07 | Source tests | `npm test --prefix frontend` | exit 0 (relevant tests) |
| U06, U08 | Backend build | `npm run build:backend` | exit 0 |
| U06, U08 | Backend tests | `npm run test --prefix backend` | exit 0 (minus known baselines) |
| U08 | Seed workflow | `npm run seed:demo` | exit 0 |

**Cross-cutting invariants** (applied to ALL units, checked by supervisor reading diffs):

| Invariant | Check Method | On Violation |
|-----------|-------------|-------------|
| No Turkish IA/routes changed | `git diff` for route renames outside unit scope | Block, report |
| No PII logged | Diff shows no emails, phones, TCKN, bodies, auth headers | Block, report |
| No scope creep | Changed files subset of unit's `fileOwnership.modify` | Block, handoff |
| No generated/dependency edits | No changes in `.next/`, `node_modules/`, `dist/` | Block |
| File size limits | No new module >200 lines; no monolith growth | Warn |
| Turkish copy preserved | Labels, placeholders unchanged unless explicitly allowed | Block |

**Integration validation** (Unit 9 only):

| Check | Details |
|-------|---------|
| Shared client contract | Verify cache→validate→retry→log order; no duplicate logs, no swallowed errors |
| Cross-unit behavior | Editorial pages render with consistent cache, validation, and media |
| No-store boundaries | Registration status and mutation paths remain uncached |
| Runtime smoke | Build both apps, start backend+frontend, load representative pages, exercise proxy routes |
| Notification plugin | Strapi starts with plugin, seed data intact, submit flows work |
| Baseline failures | Known failures from `FAILING_TESTS.md` separated from new regressions |

#### 3.3.3 Validation Execution Protocol

The supervisor runs validation in this order:

1. **Pre-dispatch**: Check state, acquire locks, verify gates
2. **Dispatch worker**: via `task` tool with `wave4-worker` agent type
3. **Wait for completion**: Worker returns results
4. **Post-edit automated**: Run build/lint/test commands
5. **Cross-cutting manual**: Read diffs, check invariants
6. **Update state**: Mark unit as `completed`, `failed`, or `blocked`
7. **Log**: Record all validation outcomes in `validationLog`

### 3.4 Component 4: Supervisor Agent

**Location**: `.kilo/agent/wave4-supervisor.md`

#### 3.4.1 Agent Configuration

```yaml
---
description: Wave 4 Supervisor — orchestrates parallel refactor execution with state tracking, validation, and error recovery.
mode: primary
model: deepseek/deepseek-reasoner
temperature: 0.15
steps: 50
permission:
  read: allow
  list: allow
  glob: allow
  grep: allow
  edit:
    ".kilo/orchestrator/*": allow
  bash:
    "*": allow           # Needs broad bash for validation commands
    "gh *": ask          # PR creation requires confirmation
    "git push*": ask
  task: allow
---
```

The supervisor needs broader bash access than typical agents because it runs validation commands (build, lint, test) across both stacks. PR creation (`gh`) and pushes are `ask`-gated for safety.

#### 3.4.2 Supervisor Lifecycle

```
Phase 0: INITIALIZE
  ├── Read plan document
  ├── Parse units using decomposition protocol
  ├── Bootstrap wave4-state.json
  ├── Read backend/tests/FAILING_TESTS.md and classify
  └── Output: ready state, ready to dispatch U00

Phase 1: EXPLORER PASS (Unit 0)
  ├── Verify P3-01 gate is satisfied
  ├── Dispatch 2-4 explorer agents (read-only) in parallel
  │   ├── Explorer A: PR_STRATEGY.md stale paths + U01-U02 surfaces
  │   ├── Explorer B: U03-U04-U05 surfaces
  │   ├── Explorer C: U06-U07 surfaces + backend tests
  │   └── Explorer D: U08 surfaces + FAILING_TESTS.md classification
  ├── Collect explorer reports
  ├── Write inventory artifact: docs/plans/...-inventory.md
  ├── Update state: mark U00 completed
  └── Output: consolidated inventory, ready for parallel workers

Phase 2: PARALLEL IMPLEMENTATION (Units 1-8)
  ├── Compute ready set (all units whose deps are satisfied)
  ├── While ready set not empty OR in-progress units exist:
  │   ├── For each ready unit:
  │   │   ├── Acquire file locks (check conflict matrix)
  │   │   ├── If locks acquired:
  │   │   │   ├── Dispatch wave4-worker via task tool
  │   │   │   └── Update state: pending→in_progress
  │   │   └── If locks blocked:
  │   │       └── Update state: pending→blocked with reason
  │   ├── Wait for worker completions (poll or collect results)
  │   ├── For each completed worker:
  │   │   ├── Run post-edit validation gates
  │   │   ├── Run cross-cutting invariant checks
  │   │   ├── If passed: update state→completed, release locks
  │   │   ├── If failed with handoffs: update state→blocked, record handoffs
  │   │   └── If failed with errors: update state→failed, decide retry/reassign
  │   ├── Recompute ready set (dependencies may have resolved)
  │   └── Handle timeouts: if worker exceeds plan-expected time, probe and decide
  └── All U01-U08 completed or blocked with documented reasons

Phase 3: INTEGRATION (Unit 9)
  ├── Verify all U01-U08 completed or blocked
  ├── Acquire exclusive lock on all shared files
  ├── Dispatch integration worker
  │   ├── Reconcile strapi-client.ts: cache→validate→retry→log order
  │   ├── Reconcile domain modules: query + cache + validation + media + filters
  │   ├── Reconcile backend: notification plugin + analytics + SPL
  │   └── Run runtime smoke gates
  ├── Run integration validation
  ├── Release locks
  └── Update state: mark U09 completed

Phase 4: REPORT
  ├── Summarize all unit statuses
  ├── List unresolved blockers (→ Wave 5/6)
  ├── List deferred items from worker handoffs
  ├── Metrics: elapsed time, units completed/failed/blocked
  └── Output: final state file updated, report in plan artifact
```

#### 3.4.3 Concurrency Management

The supervisor uses a **work-stealing pool** model:

- **Max parallel workers**: 8 (from plan's "maximum parallelism")
- **Dispatch strategy**: Greedy — dispatch any ready unit immediately
- **Shared-file throttling**: When a shared file has one in-progress unit, other units needing that file are blocked until the first completes
- **P5-05 gate**: Unit 8 is not dispatched until P1-01 is confirmed settled on the target branch
- **Timeouts**: If a worker exceeds 2× the plan's estimated effort without reporting, the supervisor probes. If unresponsive, mark as failed and retry (max 2 retries)

#### 3.4.4 Error Recovery

| Error class | Recovery strategy |
|-------------|-------------------|
| Worker reports handoff (needs file outside boundary) | Block unit, record handoff in state, coordinate with owning unit or supervisor |
| Worker crashes / timeout | Mark failed, clear file locks, retry with same assignment (max 2 retries). On third failure, mark permanently blocked with crash report |
| Validation failure (build/lint/test) | Mark failed, log exact failure output. Do NOT retry automatically — requires human review unless failure is in known baseline list |
| Shared-file conflict (two units produce incompatible changes) | Both units complete individually, Unit 9 reconciliation flag raised. Supervisor records the conflict |
| P1-01 gate not satisfied for U08 | Keep U08 in pending; do not dispatch. Report blocker |
| Pre-existing test failures mask new regressions | Use `FAILING_TESTS.md` baseline; filter known failures from validation output |

#### 3.4.5 Alignment Verification

After each phase, the supervisor checks alignment with original plan objectives:

- **Phase 1**: Did explorer inventory flag all stale paths? Is FAILING_TESTS.md classified?
- **Phase 2**: Do all 8 units have reviewable branches or documented blockers?
- **Phase 3**: Does the combined branch pass the shared client contract? Are all no-store boundaries intact?
- **Final**: Were any Wave 5/6 blockers created that need explicit handoff?

#### 3.5.2 Worker Core Instructions

The worker agent receives a highly specific prompt from the supervisor containing:

1. **Unit assignment**: Unit ID, PR ID, title, goal
2. **Write boundary**: Exact list of files it may modify/create
3. **Read boundary**: Files it may inspect but not edit
4. **Approach constraints**: Specific rules from the plan for that unit
5. **Handoff protocol**: If a required file is outside boundary, stop and report
6. **Validation expectations**: Commands to run before reporting completion
7. **Output format**: Changed files, validation results, skipped items, handoffs, branch name

The worker must:
- NOT perform broad read-only discovery (that's the explorer's job)
- NOT edit files outside its write boundary
- NOT change unrelated worktree changes
- NOT mix concerns from other units (e.g., Unit 2 must not add Zod validation)
- Preserve Turkish IA/copy and repo conventions
- Report all handoffs, blockers, and deferred items

#### 3.5.3 Worker Dispatch Template

The supervisor constructs a prompt for each worker:

```markdown
You are a Wave 4 write worker assigned to **{unitId}: {prId} {title}**.

2. `docs/plans/2026-05-03-001-refactor-wave4-parallel-delegation-inventory.md` — Unit 0 inventory
3. The unit section in `docs/plans/2026-05-03-001-refactor-wave4-parallel-delegation-plan.md`

## Your Assignment

**Goal**: {goal}

**Write boundary** (ONLY these files):
- Modify: {modifyList}
- Create: {createList}
- Test: {testList}

**Handoff boundary** (stop and report if needed):
- {handoffList}

**Constraints**:
{approachConstraints}

**Do NOT**:
- Perform broad read-only discovery or file scanning
- Edit files outside your write boundary
- Change unrelated worktree state
- Mix concerns from other units

## Validation
Before reporting completion, run:
{validationCommands}

## Output
Return in your final response:
- Changed files (with summaries)
- Validation results (commands run, exit codes, failures)
- Handoffs requested (file + reason)
- Deferred items
- Branch name created
```

## 6. Risks and Open Questions

### 6.1 Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| Plan document format changes break parsing | Medium | Supervisor uses fuzzy heading matching; minor format changes won't break. Document version pinned in state |
| Worker agents exceed step limits on large units (U08, U05) | Medium | Workers given 35 steps (higher than typical 25-30). Supervisor can split large units |
| Shared-file merge conflicts require human resolution | High | Conflict matrix + Unit 9 reconciliation designed for this. Unresolvable conflicts flagged for human |
| Pre-existing test failures confuse validation | Medium | `FAILING_TESTS.md` provides baseline filter. Supervisor subtracts known failures |
| `task` tool session length / context window limits | Medium | State file enables session resumption. Supervisor restarts from any checkpoint |
| P1-01 gate for U08 may be ambiguous | Low | Supervisor explicitly checks for settled public endpoint behavior before dispatching U08 |
| Worker scope creep into unowned files | Medium | Worker instructions forbid it. Cross-cutting validation catches. Supervisor can reject and retry |
| Explorer reports incomplete → workers work from stale paths | Medium | Supervisor validates explorer reports against current worktree before dispatching workers |

### 6.2 Open Questions

- **Should the supervisor auto-create PRs via `gh` or only create branches?** The plan defers `gh` policy to the execution runner. Supervisor creates branches and reports `gh pr create` commands; actual PR creation is gated by `bash: "gh *": ask`
- **Should workers be given exact Strapi plugin structure or discover it?** Explorers own discovery. Workers get the inventory. Unit 0 must include current Strapi 5 local-plugin convention
- **What if a worker discovers a missing earlier-wave dependency (e.g., P3-01 incomplete)?** Worker stops and reports blocker. Supervisor records it and marks unit blocked. Execution pauses until resolved
- **Should the harness support resumption after human intervention?** Yes — state file is single source of truth. Supervisor reads current state on startup and resumes from last checkpoint
