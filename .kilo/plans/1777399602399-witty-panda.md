**Unit 1 only** from the plan (backend model + endpoint):

**Write ownership:**
- Create: `backend/src/api/newsletter-subscription/content-types/newsletter-subscription/schema.json`
- Create: `backend/src/api/newsletter-subscription/controllers/newsletter-subscription.ts`
- Create: `backend/src/api/newsletter-subscription/routes/newsletter-subscription.ts`
- Create: `backend/src/api/newsletter-subscription/routes/custom-newsletter-subscription.ts`
- Create: `backend/src/api/newsletter-subscription/services/newsletter-subscription.ts`
- Create: `backend/tests/api/newsletter-subscription/service.test.ts`
- Create: `backend/tests/api/newsletter-subscription/routes.test.ts`

**Do not own:**
- Frontend files (proxy, component, visibility surfaces)
- `backend/src/index.ts` (final bootstrap reconciliation → U14 owns this)
- `backend/types/generated/contentTypes.d.ts` (U14 owns this)

**Schema fields:** `email` (email, required), `consentAccepted` (boolean, required), `consentTextSnapshot` (text), `status` (enum: active/passive/unsubscribed, default active), `sourcePage` (string), `sourceContentType` (string), `sourceContentSlug` (string), `subscribedAt` (datetime), `lastSeenAt` (datetime)

**Custom endpoint:** `POST /api/newsletter-subscriptions/subscribe`
- Normalize email to lowercase
- Upsert by email: if active duplicate, refresh `lastSeenAt` and source, return success
- Reject missing consent with 400
- Reject invalid email with 400
- Do NOT send email

**Patterns to follow:** `backend/src/api/contact-submission/` (controllers, services, routes, tests)

**Branch:** `feat/u03-newsletter-subscription-backend`

**Validation:** `npm run build:backend`, targeted subscription API tests

**Output contract:**
- Submit endpoint: `POST /api/newsletter-subscriptions/subscribe`
- Payload: `{ email, consentAccepted, sourcePage?, sourceContentType?, sourceContentSlug? }`
- Response: `{ success: true, message: "..." }`
- Error: `{ success: false, message: "...", errors: [...] }`

- Create: `backend/tests/api/analytics-event/routes.test.ts`

**Schema fields:** `eventId` (string, required, indexed), `timestamp` (datetime), `sessionId` (string), `pagePath` (string), `sourcePage` (string), `ctaId` (string), `contentType` (string), `contentSlug` (string), `backendReference` (string), `properties` (JSON, with PII stripping/allowlist enforcement)

**Custom endpoint:** `POST /api/analytics-events/capture`
- Validate `eventId` against known event IDs (read from shared catalog)
- Strip/reject PII-like keys (email, phone, name, tckn, address, etc.)
- Keep endpoint unauthenticated but validation-strict
- Fire-and-forget from frontend perspective

**Frontend proxy:** `frontend/src/app/api/analytics/events/route.ts`
- Next.js App Router route proxying to Strapi
- Does NOT expose Strapi internals
- Follows existing proxy pattern in `frontend/src/app/api/contact-submissions/submit/route.ts`

**Patterns to follow:** 
- Backend: `backend/src/api/contact-submission/`
- Frontend proxy: `frontend/src/app/api/contact-submissions/submit/route.ts`

**Branch:** `feat/u04-measurement-backend`

**Validation:** `npm run build:backend`, `npm run build:frontend`, targeted measurement tests

**Output contract:**
- Submit endpoint: `POST /api/analytics-events/capture`
- Payload shape: `{ eventId, sessionId, pagePath?, sourcePage?, ctaId?, contentType?, contentSlug?, backendReference?, properties?: Record<string, unknown> }`
- Allowed property keys: `page_path`, `source_page`, `cta_id`, `content_type`, `content_slug`, `session_id`
- Rejected keys: any containing `email`, `phone`, `name`, `tckn`, `address`, `password`
- Client captures via Next proxy: `POST /api/analytics/events`

## 4. Cross-Agent Coordination Rules

1. **No shared files between Subagents A, B, C.** Each has distinct write ownership.
2. **`backend/types/generated/contentTypes.d.ts`** — none of these subagents edit it. U14 will regenerate it once after all backend changes land.
3. **`backend/src/index.ts`** — none of these subagents edit it. U14 will add public read permissions for `blog-author` and any new permissions.
4. **Branches:** Each subagent creates its own branch (`feat/u03-*`, `feat/u04-*`, `feat/u06-*`) and opens its own PR.
5. **PR format:** Include unit ID, source plan paths, changed files, validation results, and integration handoffs in the PR body.
