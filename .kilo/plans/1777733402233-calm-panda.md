# Plan: P1-02 — Registration Race Condition, KVKK Consent, PII Leaks

## 1. Goal

Fix three interconnected security/data-integrity issues in the event registration flow:

1. **Registration race condition** — Two concurrent requests for the same student+event can create duplicate registrations.
2. **Missing server-side KVKK consent validation** — The `POST /api/registrations/register` endpoint does not validate KVKK consent at all; consent only exists as a client-side checkbox (and only for `egitim`/`kurs` event types). The frontend never transmits the consent value to the backend.
3. **PII leaks** — The registration API response returns the full student record (email, phone, name); the "already registered" error enables email enumeration; teacher email is publicly exposed via the content API.

## 3. Proposed Implementation

### 3A. Fix Race Condition (Backend)

**Root cause:** The `registerStudentForEvent` service has a read-then-write pattern spanning four separate DB queries with no transaction or unique constraint. Two concurrent requests can both pass the duplicate check before either creates the registration.

**Fix — Two layers of defense:**

**Layer 1: Wrap in `strapi.db.transaction()`**

Wrap the entire flow (event lookup → student upsert → duplicate check → create registration) inside `strapi.db.transaction(async (trx) => { ... })`. This is the same pattern already used in `backend/src/api/course-application/services/course-application.ts:257-258`.

Changes in `backend/src/api/registration/services/registration.ts`:
- Wrap steps 3b–3h in `strapi.db.transaction()`
- Move the notification send (step 3i) **outside** the transaction (fire-and-forget; should not block commit)
- Return sanitized registration data (see 3C)

**Layer 2: Add unique constraint on `(student_id, event_id)`**

Add a `UNIQUE` constraint in SQLite via bootstrap in `backend/src/index.ts`:
```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_registration_student_event 
ON registrations (student_id, event_id)
```

Also optionally add a `beforeCreate` lifecycle hook in `backend/src/api/registration/content-types/registration/lifecycles.ts` as an extra guard.

The transaction is the primary fix; the DB constraint is the safety net.

Also fix the `upsertByEmail` race in `backend/src/api/student/services/student.ts`:
- Catch SQLite `UNIQUE constraint failed` errors on `create()` and retry the `findOne` + `update` path

**Files to change:**
- `backend/src/api/registration/services/registration.ts` — wrap in transaction
- `backend/src/api/student/services/student.ts` — handle UNIQUE violation on create retry
- `backend/src/index.ts` — add unique index creation in bootstrap
- `backend/src/api/registration/content-types/registration/lifecycles.ts` (new) — optional beforeCreate hook as extra guard

### 3B. Add Server-Side KVKK Consent Validation (Backend + Frontend)

**Root cause:** The backend controller never validates KVKK consent. The frontend checkbox is shown only for `egitim`/`kurs` events and its value is never transmitted to the API — meaning an attacker can POST directly to the backend and bypass the consent requirement entirely.

**Business rule:** `etkinlik` events do NOT require KVKK consent. Only `egitim` and `kurs` events require it. The backend must become event-type-aware to enforce this conditionally.

**Fix:**

**Backend service** — `backend/src/api/registration/services/registration.ts`:
- Add `eventType` to the event `select` array (currently: `['id', 'documentId', 'title', 'slug', 'startsAt', 'keepRegistrationsOpen']`) → add `'eventType'`
- After the event is fetched and validated, check: if `event.eventType` is `'egitim'` or `'kurs'` AND `input.kvkkConsent` is not `true`, throw `ValidationError('kvkkConsent must be true')`
- This keeps the validation close to the data it depends on (the event type)

**Backend controller** — `backend/src/api/registration/controllers/registration.ts`:
- Extract `kvkkConsent` from the request body (alongside existing field extraction)
- Pass `kvkkConsent` to the service call in `registerStudentForEvent({ ... input })`
- The validation logic itself lives in the service (not the controller), because the controller doesn't have the event type

**Frontend** — `frontend/src/hooks/use-event-registration-form.ts`:
- **Keep** the existing conditional client-side validation (`requiresKvkkConsent`) — no UI change
- **Send** `kvkkConsent: values.kvkkConsent` in the request body (currently NOT sent at all)
- For `etkinlik` events: the checkbox is not rendered, so `values.kvkkConsent` will be `false` (initial state), but the backend won't require it for this event type
- Add error message mapping for `"kvkkConsent must be true"` → Turkish: `"KVKK aydınlatma metnini onaylamanız gerekmektedir."`

**Frontend form** — `frontend/src/components/event-registration-form.tsx`:
- **No changes** — checkbox remains conditionally shown based on `requiresKvkkConsent` (only for `egitim`/`kurs`)

**Files to change:**
- `backend/src/api/registration/services/registration.ts` — select `eventType`, add conditional KVKK validation
- `backend/src/api/registration/controllers/registration.ts` — extract and pass `kvkkConsent` to service
- `frontend/src/hooks/use-event-registration-form.ts` — send `kvkkConsent` to backend, add error translation
- `frontend/src/components/event-registration-form.tsx` — NO changes (stays as-is)

### 3C. Fix PII Leaks (Backend + Frontend)

**Three leaks to address:**

**Leak 1: Registration API returns full student PII**

`backend/src/api/registration/services/registration.ts:57-68` creates the registration with `populate: { event: true, student: true }` and returns the full populated object. The controller sends this directly to the client.

Fix: Return a sanitized object instead of the full registration record. The frontend doesn't use the response body for anything beyond checking `response.ok`.

Return format:
```ts
{
  id: registration.id,
  status: registration.status,
  event: {
    documentId: registration.event.documentId,
    title: registration.event.title,
  },
}
```

This mirrors the sanitization pattern used in course-application service (lines 320-332).

The notification payload building (lines 70-98) already accesses `registration.student` and `registration.event` individually — keep the full population for notification use, but return the sanitized version to the controller.

**Leak 2: "Already registered" error enables email enumeration**

Fix: Instead of throwing an error for duplicates, make the registration **idempotent**:
- If an existing registration is found, return success with the same sanitized response as a new registration
- The student sees "Kayıt başarılı" both for new and existing registrations
- Remove the duplicate error mapping from the frontend (`use-event-registration-form.ts:47-49`)

This eliminates the enumeration vector entirely.

**Leak 3: Teacher email publicly exposed**

`backend/src/index.ts:4-5` grants public `find`/`findOne` on `teacher`, and the teacher schema includes an `email` field. The frontend displays teacher email at `frontend/src/app/egitmenler/[slug]/page.tsx:89-101`.

**Recommendation:** Keep as-is. Teacher emails are `@netas-academy.local` in demo data and are displayed as public professional contact info intentionally. This is not a PII leak — it's a public directory. **No code change needed for this item**, but flag for product review.

**Files to change:**
- `backend/src/api/registration/services/registration.ts` — sanitize return value; make duplicates idempotent
- `backend/src/api/registration/controllers/registration.ts` — adjust response wrapping to match sanitized output
- `frontend/src/hooks/use-event-registration-form.ts` — remove "already registered" error mapping (lines 47-49)

## 5. Risks and Open Questions

### Risks

| Risk | Mitigation |
|---|---|
| `strapi.db.transaction()` behavior with SQLite — Strapi 5 may not fully support transactions with the query engine API | Verify with a quick test before committing. The course-application service already uses it successfully. |
| Breaking existing frontend behavior — frontend currently doesn't send `kvkkConsent` | Add `kvkkConsent` to the request body. For etkinlik events, it will be `false` and the backend will accept it. For egitim/kurs events, it must be `true` (enforced by both client-side checkbox validation and server-side check). |
| Idempotent duplicate handling may cause extra admin notifications — admins get a notification even for duplicate submissions | Acceptable trade-off. The notification includes `registrationId` which admins can use to verify that a new registration was not actually created. |
| Removing "already registered" error message might confuse users who forgot they registered | The success message is generic: "Kaydınız alındı. Ekibimiz kısa süre içinde sizinle iletişime geçecek." This is appropriate for both new and returning users. |
| Unique index migration on existing DB may fail if duplicates already exist | Bootstrap code should use `CREATE UNIQUE INDEX IF NOT EXISTS` and wrap in try-catch. If duplicates exist, log a warning but don't crash startup. |

### Open Questions

1. **Should internal notification emails still carry full PII?** Current plan defers this — notification emails to internal admins carrying masked TCKN and plaintext email/phone is common industry practice for operational notifications. Can be addressed in a separate P2 issue if needed.

2. **Rate limiting on the register endpoint?** The endpoint is public with no auth and no rate limiting. While not in scope for this P1, it should be tracked as a follow-up (HTTP 429 via middleware or proxy).

3. **TCKN_STORAGE_PEPPER optional?** The TCKN hashing pepper is optional. Consider making it required in production with a startup guard. Deferred to a separate issue.
