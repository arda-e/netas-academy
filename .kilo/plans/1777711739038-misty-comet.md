# P2-02: Fix TCKN sessionStorage exposure and unify TCKN validation

## 1. Goal

Address three related audit findings:

- **SEC-003**: Stop persisting TCKN (Turkish ID) to `sessionStorage` in the event registration form.
- **AR-008**: Deduplicate the `FormStorage` save/restore pattern with a new `useFormPersistence` React hook.
- **AR-002**: Add cross-reference comments between frontend and backend TCKN validation implementations so future changes stay synchronized.

---

## 2. Relevant code paths

| File | Purpose |
|------|---------|
| `frontend/src/lib/form-storage.ts` | Thin `sessionStorage` wrapper with `save/load/clear` — target for `excludeFields` filtering |
| `frontend/src/hooks/use-event-registration-form.ts` | Persists TCKN via `storage.save(values)` on every keystroke — primary fix location |
| `frontend/src/components/contact/intent-lead-form.tsx` | Uses `FormStorage` with same save/restore pattern (no TCKN field) — hook migration target |
| `frontend/src/lib/tckn.ts` | Frontend TCKN validation (`isValidTckn`, `normalizeTcknValue`) — add cross-ref comment |
| `backend/src/utils/tckn.ts` | Backend TCKN validation + masking + hashing — add cross-ref comment |
| `frontend/package.json` | Test runner: `node:test` with `.test.mjs` files in `src/__tests__/` |
| `backend/package.json` | Test runner: `vitest`, files in `backend/tests/` |

**Data flow where TCKN is exposed:**
```
useEventRegistrationForm
  → useState init: FormStorage.load() ← reads sessionStorage
  → useEffect on [values]: FormStorage.save(values) ← writes TCKN to sessionStorage every keystroke
  → handleSubmit success: FormStorage.clear() + setValues(initialValues)
```

`IntentLeadForm` follows the same pattern but its `FormValues` type has `fullName` instead of `tckn`, so it does not expose TCKN. It does store `email`, `phone`, and `fullName` in sessionStorage — those are PII but out of scope for this ticket.

## 3. Proposed implementation

### 3A. Add `excludeFields` option to `FormStorage.save()`

**File:** `frontend/src/lib/form-storage.ts`

- Add an optional second parameter to `save()`:
  ```ts
  save<T>(data: T, options?: { excludeFields?: (keyof T)[] }): void
  ```
- When `excludeFields` is non-empty, create a shallow copy of `data`, delete each excluded field, and serialize the filtered object.
- `load()` and `clear()` are unchanged. The caller decides which fields to exclude at save time.
- Backward compatible: existing callers that omit the second argument behave identically.

**Rationale:** This is the narrowest change that fixes the security bug. The `FormStorage` class is a generic utility and should not hardcode TCKN knowledge. Each consumer knows which fields are sensitive.

---

### 3B. Create `useFormPersistence` hook

**File (NEW):** `frontend/src/hooks/use-form-persistence.ts`

Provide a React hook that wraps the common `FormStorage` load/save/clear lifecycle:

```ts
function useFormPersistence<T extends Record<string, unknown>>(
  storageKey: string,
  options?: { sensitiveFields?: (keyof T)[] }
): {
  load: () => T | null;
  save: (data: T) => void;
  clear: () => void;
}
```

- `storageKey` is memoized so a new `FormStorage` is only created when the key changes.
- `save` automatically calls `FormStorage.save(data, { excludeFields: options?.sensitiveFields })`.
- `load` and `clear` delegate directly to `FormStorage`.
- All three methods are stable references (via `useCallback`).

**Rationale:** This centralizes the "create FormStorage → save with sensitive field filtering" pattern so neither consumer needs to remember to pass `excludeFields` manually.

---

### 3C. Refactor `useEventRegistrationForm` to use the new hook

**File:** `frontend/src/hooks/use-event-registration-form.ts`

**Changes:**
- Import `useFormPersistence` instead of `FormStorage`.
- Replace:
  ```ts
  const storage = useMemo(() => new FormStorage(`event-registration-${eventDocumentId}`), [eventDocumentId]);
  const [values, setValues] = useState(() => storage.load<EventRegistrationValues>() ?? initialValues);
  useEffect(() => { storage.save(values); }, [values, storage]);
  // on success: storage.clear();
  ```
  with:
  ```ts
  const { load, save, clear: clearStorage } = useFormPersistence<EventRegistrationValues>(
    `event-registration-${eventDocumentId}`,
    { sensitiveFields: ['tckn'] }
  );
  const [values, setValues] = useState(() => load() ?? initialValues);
  useEffect(() => { save(values); }, [values, save]);
  // on success: clearStorage();
  ```
- Remove the `FormStorage` import.

**Effect:** TCKN is never written to `sessionStorage`. The rest of the form behavior (restore on mount, persist on change, clear on success) is unchanged.

### 3D. Refactor `IntentLeadForm` to use the new hook

**File:** `frontend/src/components/contact/intent-lead-form.tsx`

**Changes:**
- Import `useFormPersistence` instead of `FormStorage`.
- Remove the `storageFor()` helper function.
- Inside the component, call:
  ```ts
  const { load, save, clear: clearStorage } = useFormPersistence<FormValues>(
    `contact-form-${leadType}`,
    { sensitiveFields: [] }  // no sensitive fields in this form, but using the hook for consistency
  );
  ```
- Note: the `leadType` is state that can change. The hook re-creates `FormStorage` when the key changes (via `useMemo`).
- Replace all `storageFor(leadType).save(...)`, `.load(...)`, `.clear()` calls with the hook methods.
- **One special case:** The initial mount restore uses `initialLeadType` (from URL params), not `leadType` (which may have already changed on re-render). This requires calling `useFormPersistence` a second time with `initialLeadType` just for the initial load, OR extracting the initial load into a plain `FormStorage` call. **Decision:** Keep the mount-time restore using a direct `new FormStorage(`contact-form-${initialLeadType}`).load()` call (avoiding hook complication), and use the hook for all save/clear operations with the current `leadType`.

**Rationale:** Deduplicates the persistence pattern. The intent lead form has no TCKN field, so the `sensitiveFields` is empty — the value is in architectural consistency.

### 3F. Write tests

#### F1 — `FormStorage` sensitive field filtering test

**File (NEW):** `frontend/src/__tests__/form-storage-source.test.mjs`

Follow the existing frontend test pattern (Node `node:test` + inline `assert`). Re-implement the `FormStorage.save()` filtering logic and test:

- `save()` with no `excludeFields` stores all fields
- `save()` with `excludeFields: ['tckn']` stores all fields except `tckn`
- `save()` with multiple excluded fields strips all of them
- `save()` with empty `excludeFields` array behaves identically to no option
- `save()` with field not present in data does not throw

**File (NEW):** `frontend/src/__tests__/tckn-validation-consistency-source.test.mjs`

#### F3 — TCKN validation cross-stack consistency test (backend)

**File (NEW):** `backend/tests/unit/utils/tckn-validation-consistency.test.ts`

Use Vitest `describe`/`it`/`expect`. Import `isValidTckn` from `backend/src/utils/tckn.ts` and run the **same** test input set as F2. Assert identical results.

**Shared test vectors (use in both F2 and F3):**

| Input | Expected | Rationale |
|-------|----------|-----------|
| `"12345678901"` | `true` | Known valid checksum (last digit = sum of first 10 mod 10) |
| `"10000000146"` | `true` | Atatürk's TCKN (well-known valid) |
| `"00000000000"` | `false` | First digit cannot be 0 |
| `"1234567890"` | `false` | Too short (10 digits) |
| `"123456789012"` | `false` | Too long (12 digits) |
| `"1234567890a"` | `false` | Non-numeric |
| `"123 456 789 01"` | `true` | Normalization removes spaces, same checksum |
| `"98765432109"` | `true` | Another valid algorithmic TCKN |
| `"11111111111"` | `false` | All same digit — typically fails checksum |

**Note:** `12345678901` is already used as a valid TCKN in backend service tests (`backend/tests/api/registration/service.test.ts`, line 103). Verify its checksum before finalizing. If it doesn't pass, pick a synthetic valid one: digit 10 = `(oddSum*7 - evenSum) % 10`, digit 11 = `sum(first 10) % 10`.

## 5. Risks and open questions

### Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| TCKN field not restored after page reload | LOW | Expected behavior per acceptance criteria ("TCKN field is empty (not restored)") |
| `excludeFields` shallow copy loses class instances | NONE | Form values are always plain objects (from `useState` or `react-hook-form`) |
| IntentLeadForm `leadType` changes mid-session → storage key mismatch | LOW | Hook re-memoizes when key changes; initial load uses `initialLeadType` directly |
| TCKN test vector `12345678901` fails checksum | LOW | Verify before finalizing; use a synthetic valid TCKN if needed |

### Open questions

1. **Should `kvkkConsent` also be excluded from sessionStorage?** The audit finding (SEC-003 remediation option c) suggests skipping both `tckn` and `kvkkConsent`. `kvkkConsent` is a boolean — not PII itself — but it is bundled with PII. **Decision:** Only exclude `tckn` for now. `kvkkConsent` is not sensitive data.

2. **Should `email`, `phone`, `firstName`, `lastName` also be excluded from sessionStorage?** They are PII stored in plaintext. The finding only requires filtering `tckn`. **Decision:** Out of scope for this ticket. A follow-up ticket can expand the sensitive fields list.

3. **Should the `useFormPersistence` hook also handle `react-hook-form` integration (load → reset, watch → save)?** The hook currently provides generic `load/save/clear` methods. Full react-hook-form integration (auto-reset on load, auto-save on watch) is possible but adds complexity. **Decision:** Keep the hook simple — provide only the storage methods. Consumers handle their own form library integration.

4. **TCKN test vectors:** `12345678901` is used in backend service tests but its checksum validity needs to be verified at implementation time. Atatürk's TCKN `10000000146` is a well-known valid one.
