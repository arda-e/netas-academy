# Test Coverage Report — Implementation Plan

## 1. Goal

Generate a one-time test-coverage snapshot report for the monorepo, covering:
- **Backend unit/integration tests** (Vitest, 22 test files)
- **Frontend unit tests** (Node.js built-in `node:test`, 27 test files)
- **End-to-end tests** (currently none — document the gap)

The final deliverable is `docs/test-coverage-report.md` — a single report file summarizing coverage percentages, gaps, known failures, and a comprehensive recommendations roadmap.

## 2. Current State

| Layer | Test Runner | Test Files | Coverage Configured? | Test Script? |
|-------|------------|-----------|---------------------|-------------|
| Backend | Vitest v4.1.4 | 22 `.test.ts` + 1 `.test.js` | ❌ No | ✅ `npm test` → `vitest run` |
| Frontend | `node:test` (built-in) | 27 `.test.mjs` + 1 `.test.ts` | ❌ No | ❌ No script; manual `node <file>` |
| Root / E2E | None | 0 | ❌ No | ❌ No |

Known issues:
- Backend has **16 pre-existing test failures** across 5 test files (documented in `backend/tests/FAILING_TESTS.md`). These are documented in the report — no fix plan is included.
- Frontend tests are **static source-code analysis** — they `readFileSync` and `assert.match()` on string content; no runtime component/DOM coverage
- No e2e framework (Playwright/Cypress) installed anywhere

## 3. Proposed Implementation

The work is broken into **four subtasks**, delegated via the `task` tool. Subtasks A, B, C run in parallel; Subtask D runs after they complete to consolidate results into the final report.

---

### Subtask A: Backend Coverage

**Agent:** `general` (write code + run commands)

**Objective:** Install Vitest coverage provider, run all backend tests with coverage, capture results.

**Steps:**
1. Install coverage provider in `backend/`:
   ```bash
   npm install -D @vitest/coverage-v8
   ```
2. Add a coverage script to `backend/package.json`:
   ```json
   "test:coverage": "vitest run --coverage"
   ```
3. Run `npm run test:coverage` from the backend directory (append `|| true` to handle known failures non-fatally while still generating coverage data)
4. Capture and return:
   - Coverage percentages (lines, branches, functions, statements)
   - Per-file coverage data (which files have 0% vs 100%)
   - Pass/fail/skip counts
   - Path to generated coverage report (HTML/JSON) if any
   - The 16 known failures and their impact on coverage numbers

**Return format:** Structured summary with raw numbers and a list of uncovered backend modules.

---

### Subtask B: Frontend Coverage

**Agent:** `general` (write code + run commands)

**Objective:** Create a test runner script that collects all `.test.mjs` files and runs them with Node's experimental coverage flag, then capture results.

**Steps:**
1. Create `frontend/scripts/run-tests-with-coverage.mjs` that:
   - Reads all `.test.mjs` files from `frontend/src/__tests__/` via `fs.readdirSync`
   - Dynamically `import()`'s each test file sequentially
   - Wraps them in `node:test` suites so coverage is collected across all files
2. Add a `test:coverage` script to `frontend/package.json`:
   ```json
   "test:coverage": "node --experimental-test-coverage --test-reporter=spec scripts/run-tests-with-coverage.mjs"
   ```
3. For the single `.test.ts` file (`responsive-layout.test.ts`), attempt:
   ```bash
   npx tsx --test --experimental-test-coverage src/components/content/responsive-layout.test.ts
   ```
   If `tsx` doesn't support the coverage flag, document the gap and skip it.
4. Run the coverage scripts from the frontend directory
5. Capture and return:
   - Coverage percentages (lines, branches, functions, statements)
   - Per-file coverage data
   - Pass/fail counts
   - **Methodology caveat:** These are source-analysis tests — coverage reflects which source files were read/analyzed, not runtime execution paths. This must be prominently documented.

**Return format:** Structured summary with raw numbers and a prominent note about the coverage methodology limitation.

---

### Subtask C: E2E Coverage Analysis

**Agent:** `explore` (read-only research)

**Objective:** Confirm zero e2e coverage exists and document which routes would benefit most from future e2e investment.

**Steps:**
1. Re-verify across the entire repo: no `playwright`, `cypress`, `selenium` configs, test files, or npm dependencies
2. Search for any existing browser-test artifacts (screenshots, videos, traces)
3. Document the gap clearly: 0% e2e coverage, no framework installed
4. Produce a prioritized list of routes/pages for future e2e investment:
   - `/etkinlikler` — events + registration flow (high priority, form submission)
   - `/iletisim` — contact form (high priority, form submission)
   - `/egitimler` — courses listing (medium priority, data-driven)
   - `/blog-yazilari` — blog posts (medium priority, data-driven)
   - `/haberler` — news (low priority)
   - `/` — marketing hero (low priority, static content)

**Return format:** Confirmation of zero e2e coverage + prioritized route list with rationale for each priority level.

---

### Subtask D: Consolidate & Generate Final Report

**Agent:** `general` (aggregate results from A, B, C and write final report)

**IMPORTANT:** This task runs AFTER A, B, C are complete. Provide it with the results returned by each subtask.

**Steps:**
1. Aggregate coverage data from all three subtasks into a single unified view:
   - Backend coverage (Vitest — lines, branches, functions, statements)
   - Frontend coverage (node:test — with methodology caveat)
   - E2E coverage (0% — gap documented)
2. Incorporate known failures and their impact on coverage accuracy (document only, no fix plan)
3. Document methodology limitations prominently (frontend source-only tests)
4. Write the final report to `docs/test-coverage-report.md` with these sections:
   - **Executive Summary** — high-level numbers, verdict, top 3 gaps
   - **Backend Coverage** — percentages, pass/fail counts, uncovered modules, known failures table
   - **Frontend Coverage** — percentages, pass/fail counts, methodology caveat (source-code analysis only)
   - **E2E Coverage** — 0%, gap analysis, prioritized route list for future investment
   - **Known Failures** — summary table from `FAILING_TESTS.md` (document only, no fix proposals)
   - **Recommendations** — comprehensive roadmap (NOT just quick wins):
     1. Add e2e testing framework (Playwright recommended) and cover registration + contact flows first
     2. Add test runner and script for frontend tests (`npm test` in frontend)
     3. Convert frontend source-analysis tests to runtime component tests (Jest + Testing Library or Vitest)
     4. Add CI pipeline with test execution on PRs
     5. Fix 16 known backend test failures
     6. Set coverage thresholds for backend (e.g., 70% lines, 60% branches)
     7. Add coverage collection for frontend runtime tests once migrated
     8. Expand backend test coverage for uncovered modules
     9. Add e2e coverage for remaining routes (courses, blog, news, home)
5. Return: path to `docs/test-coverage-report.md` and a 3-sentence executive summary.

**Return format:** Path to the generated report and a brief executive summary.

---

## 4. Execution Order

```
Phase 1 (parallel):   Subtask A + Subtask B + Subtask C
Phase 2 (sequential): Subtask D (depends on A, B, C results)
```

Phase 1 tasks are independent and can run simultaneously. Subtask D must wait for all three results.

## 6. Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| `--experimental-test-coverage` may fail with dynamic `import()` of `.mjs` files | Subtask B: test with a single file first; fall back to running each `.mjs` individually and aggregating coverage JSON |
| `tsx` may not support `--experimental-test-coverage` | Subtask B: document the gap; the 26 `.mjs` files are the bulk of coverage |
| Vitest `@vitest/coverage-v8` needs native addon compilation | Fall back to `@vitest/coverage-istanbul` if v8 fails |
| 16 known failures cause vitest non-zero exit | Append `|| true` to the command; coverage data is still generated despite test failures |
| Frontend coverage numbers are misleading (source-only tests) | Document this caveat prominently in both Subtask B output and the final report |
| Zero e2e infrastructure | Expected — report it as a gap with prioritized recommendations |

## 7. Validation

After all subtasks complete and the report is generated:
- Verify `docs/test-coverage-report.md` exists and is well-formed
- Spot-check coverage numbers against raw output from subtasks A and B
- Ensure the report mentions: known failures, methodology limitations, e2e gap, and comprehensive roadmap
